# 记忆与上下文交付设计方案（OpenViking 替代）

> 版本：v0.2（2026-08）｜ 状态：设计稿，待评审｜ 关联文档：[PersonLLMWiki 设计规范](01-PersonLLMWiki设计规范.md)、[架构与集成](../01-架构/01-架构与集成.md)
>
> **v0.2 变更**：
> ① 记忆采集由「会话结束钩子」升级为「过程级 hook + 原始 trace 层」（借鉴 ai-memory）；
> ② `decision` 记忆结构化并纳入知识星链图谱（借鉴 semantica）；
> ③ 新增「记忆管理页」规划：独立顶级菜单「记忆」（M4 建立），记忆转正入口落此（回答评审要点 2/3）。

## 1. 背景与目标

### 1.1 背景

本机集成过 OpenViking（自进化上下文数据库，`@openviking/dsh-memory-plugin`），其定位是面向 AI Agent 的「记忆 + 资源(RAG) + 技能」统一上下文底座。评估后认为其本机形态偏重：

- 依赖 Docker 服务端常驻（`127.0.0.1:1933`），服务端离线则召回/沉淀能力全部不可用；
- 与 PLW 的「知识 RAG」能力高度重叠，且 PLW 在可信度侧更强（人工审批、来源溯源、知识图谱）；
- 跨 Harness 兼容（Claude Code/Codex/Cursor）对本机「单 DSH 生态」用户无实际收益。

**目标**：PLW 补齐 OpenViking 的差异化缺口——**会话记忆自动提取、分层上下文交付、技能沉淀**，以单 Python 进程实现 OpenViking 的核心价值，去掉 Docker 服务端依赖。

### 1.2 替代范围对照

| OpenViking 能力 | PLW 现状 | 本方案动作 |
|---|---|---|
| 知识 RAG（resources） | ✅ 已有且更强（编译/审批/溯源/图谱） | 不动 |
| MCP 工具面 | ✅ 已有（19+ 工具） | 新增记忆类工具 |
| 会话记忆自动提取 | ❌ 无（`src/` 零 memory 实现） | **新增记忆模块**（§3） |
| 分层上下文交付 | ❌ 直接 Top-K 注入 | **新增 context_assembler**（§4） |
| 技能自动沉淀 | ❌ SKILL.md 仅手写 | **新增沉淀管道**（§5） |
| 跨 Harness 插件 | ⚠️ 仅绑定 DSH | 暂不做（§9 排除项） |
| 云端/多租户 | ❌ | 暂不做（§9 排除项） |

## 2. 总体设计

### 2.1 核心决策：记忆/知识双轨制

OpenViking 的哲学是「自动沉淀、随用随长」，代价是记忆带噪音；PLW 的立身之本是「人工审批、可信溯源」。两者不可互相污染，采用**双轨制**：

| 轨 | 内容 | 入库方式 | 可信度 | 生命周期 |
|---|---|---|---|---|
| **记忆轨** | 会话提取的偏好/事实/决策（碎片化、演进中） | 自动写入，`status=auto` | 低（标注来源对话 id） | 可一键撤回（revoke） |
| **知识轨** | Wiki 概念页（编译产物） | LLM 编译 → 人工审批 | 高（来源溯源 `^[source]`） | 审批制，LLM 不可自审批 |

- 记忆轨**不进入** wiki 概念索引，独立 `memories/` 目录 + 独立检索；
- 对话注入时记忆轨按「偏好/事实」加权靠前（个性化），知识轨按「查询相关度」排序（事实权威）；
- 记忆可被用户「转正」为知识：一键发起编译任务，把记忆条目作为文章源进入审批流。

### 2.2 架构位置

```
modules/memory/                     ← 新增模块（记忆轨）
├── trace.py                        过程级 hook 采集（用户消息/工具调用/会话边界）→ 原始 trace 落盘
├── extractor.py                    复用 wiki/compiler/extractor.py 的 LLM 提取
├── pipeline.py                     trace → 异步提炼 → 去重 → 写入 → 索引（两阶段，§3.2）
├── storage.py                      memories/*.md 读写 + memories/_raw/ 原始 trace（复用 wiki 页存储模式）
├── retrieval.py                    记忆语义检索（复用 wiki/compiler/retrieval.py，按 kind 过滤）
├── injector.py                     对话开场自动召回注入上下文
├── routes.py                       REST API + MCP 工具注册
└── templates/memory.html + static  记忆管理页（独立顶级菜单，M4 建立，§3.5）

common/context_assembler.py         ← 新增（分层交付，§4）

~/.personllmwiki/skills/candidates/              ← 新增目录（技能沉淀草稿，§5）
```

### 2.3 与 DSH 的边界更新

原边界（[架构与集成](../01-架构/01-架构与集成.md)）：DSH 管「执行编排 + 记忆」，PLW 管「内容与企业能力」。

本方案将**记忆归属划入 PLW 知识底座**：PLW 已具备 LLM 提取 + embedding 索引 + 增量哈希全套基建，且记忆以 MCP 工具面（`mcp__personllmwiki__*`）供给，天然跨会话、跨 DSH 升级。DSH 仍管执行编排；PLW 提供「可检索、可注入、可撤回」的记忆资产。边界规则更新为：**PLW 管「知识 + 记忆」供给，DSH 管「执行编排」消费**。

## 3. 记忆模块

### 3.1 数据模型

存储为 Markdown + JSON frontmatter（与 wiki/concepts 一致），位于 `{RESOURCE_BASE_PATH}/memories/`：

```markdown
---
slug: 用户偏好-工作模式
kind: preference            # preference | fact | decision | other
status: auto                # auto(自动) | promoted(转正为知识) | revoked(撤回)
source_chat_id: 42          # 来源对话会话 id
created_at: 2026-08-24T10:00:00
embedding: ...              # 由索引写入，不入 md
---
正文：用户习惯在工作区先看 TODO 再开始编码。
```

关联概念：`[[相关wiki概念]]` 链接（若有），便于记忆 → 知识跳转。

**decision 结构化（借鉴 semantica）**：`kind=decision` 条目不只是一句结论，frontmatter 额外携带 `basis`（决策依据）、`source_refs`（来源对话/文章引用）、`related_entities`（关联实体/概念 slug）；这些关联关系同步写入知识星链（扩展 `get_graph` 支持记忆节点），使「决策 → 依据 → 来源 → 关联」可追溯（取 PROV-O 溯源思想，不做标准导出）。

### 3.2 提取管道（两阶段：采集 + 提炼）

**阶段一：过程级采集（fire-and-forget hook，借鉴 ai-memory）**

在 `common/agent.py` 的 Agent 循环挂 hook，每轮不阻塞地落一条原始 trace（不依赖会话结束）：

```
用户消息 / 工具调用（name + arguments + result）/ 会话边界（新建/结束）
  → trace.py 采集 → 写入 memories/_raw/（或 SQLite trace 表）
```

原始 trace 只做「原始证据留证」，不直接作为记忆条目；记忆条目的 `source_chat_id` 指向 trace，撤回后仍可审计。

**阶段二：异步提炼（复用现有编译基建）**

```
异步任务（后台线程/APScheduler，不阻塞响应）
  → extractor.extract(trace 快照)            # 复用 wiki/compiler/extractor.py，prompt 换为记忆提取
  → merge_concepts() 去重合并（同 slug 近似条目，复用 wiki/compiler/extractor.py 的 merge_concepts()）
  → 写入 memories/*.md（status=auto，带 source_chat_id）
  → 增量索引（复用 hasher.py SHA-256 变更检测，避免全量重算 embedding）
```

**触发时机**：采集持续全自动；提炼按「会话自然结束（> N 条消息且有实质内容）」「trace 积压达到阈值」「用户主动『记住本对话』」三选一触发；频率限制防噪音（如每分钟最多提炼 1 次）。

### 3.3 召回与注入

- **主动注入**：对话开场，`injector.py` 自动 `search_memory(首条用户消息)` Top-3 注入系统上下文（与 Wiki 上下文并列，`---` 分隔）；
- **按需检索**：LLM 可通过 MCP 工具主动调 `search_memory`；
- **排序**：`preference/fact` 权重 > `decision/other`，且 `status=revoked` 一律过滤。

### 3.4 MCP 工具扩展

| 工具 | 说明 | 权限 |
|---|---|---|
| `remember` | 手动写入一条记忆（LLM 或用户经 UI 触发） | 写 |
| `search_memory` | 语义检索记忆，`kind` 过滤 | 读 |
| `list_memories` | 列出记忆（按 kind/时间/状态） | 读 |
| `forget_memory` | 撤回一条记忆（`status=revoked`，物理保留可审计） | 写 |

安全约束沿用现有规则：路径越界检测、不提供物理删除（撤回制）、LLM 不可自审批转正。

### 3.5 记忆管理页（独立顶级菜单，M4 建立）

- **形态**：侧边栏新增**独立顶级菜单「记忆」**（紧邻「Wiki」，表达双轨并列），**不做成 Wiki 的子页签**——避免视觉上暗示「记忆是知识的一部分」，模糊「记忆低可信可撤回 / 知识人工审批高可信」的边界。
- **页面**：复刻 Wiki 卡片模式——tab 按 `kind` 分组（全部/偏好/事实/决策/其他），卡片显示正文 + kind 标签 + 来源对话（可跳转）+ 状态（auto/promoted/revoked）。
- **操作栏**：查看原文 / **转正为知识**（发起编译进审批流，跳转 Wiki 候选）/ **撤回**（二次确认，`status=revoked` 软删除）；页内提供「显示已撤回」过滤。
- **转正入口定在记忆管理页**（回答评审要点 3）：用户在回顾记忆时决定哪条值得沉淀为可信知识，上下文最自然。
- **约束**：`forget_memory` 必须用户二次确认，LLM 不可单独触发撤回；`promoted` 条目可跳转对应 Wiki 候选/审批页，形成「记忆 → 知识」可视化闭环。
- **时序**：M1~M2 阶段先在对话页做轻量入口（「本次会话提取了 N 条记忆」+ 可展开查看），验证提取与注入链路；正式「记忆」菜单与管理页在 M4 落地。

## 4. 分层上下文交付

### 4.1 目标

OpenViking 的核心差异点是「摘要 → 命中片段 → 原文」按需分层展开、控制 token 预算；PLW 现状是把 Top-K 片段一次性注入。新增 `common/context_assembler.py` 按预算组装。

### 4.2 组装策略

```
输入：query, 命中列表（含 wiki 页 summary + 片段 + 源文章路径）, budget_tokens, 目标层级
输出：分层上下文块

层1 摘要层：每个命中 wiki 页的 summary（~10% 预算）——让模型先有全局轮廓
层2 片段层：Top-K 命中片段 + 来源溯源（~60% 预算）——支撑具体论证
层3 原文层：需要精读的完整文章/页面（~30% 预算）——LLM 认为不够时经 MCP 工具二次拉取
```

- 层2 若预算不足则按相似度截断；层3 永不主动全量注入，由 LLM 调 `read_note`/`read_wiki_page` 按需拉取；
- 每层之间用结构化分隔符标注层级，便于模型区分「概要」与「事实」可信度。

### 4.3 接口

- **REST/MCP 兼容**：`search_kb` 扩展参数 `delivery=layered&budget_tokens=N`（默认保持 flat 兼容现有调用方）；
- **对话注入**：`common/agent.py` 的 Wiki 上下文注入改走 assembler，`expert` 模式强制分层组装。

## 5. 技能沉淀

### 5.1 流程

```
会话中 LLM 识别「可复用操作流程」（用户重复性任务/新工作流）
  → 生成 SKILL.md 草案（name/description front matter + 步骤指令，可附 scripts/）
  → 写入 ~/.personllmwiki/skills/candidates/<name>/SKILL.md（candidate 状态，不生效）
  → 前端「技能」标签页展示候选，复用 wiki 候选审批交互
    → 审批通过：移入 ~/.personllmwiki/skills/<name>/（skill_loader.py 扫描即生效，零重启）
    → 拒绝：删除候选目录
```

### 5.2 与现有机制衔接

- `common/skill_loader.py` 只扫描 `~/.personllmwiki/skills/*/SKILL.md`，候选目录 `~/.personllmwiki/skills/candidates/` 天然不加载——无需改动加载器；
- 审批交互复用 wiki 的 pending/approve/reject 模式（`WikiPage.status` 同款语义，新增 `SkillCandidate` 模型或复用表加 kind）。

## 7. 安全与隐私

- 记忆为本地文件 + 本地 embedding（fastembed ONNX），**零云依赖**，不随任何上传外泄；
- 撤回制（revoke）而非物理删除，保留审计可恢复；`forget_memory` 需要用户确认（前端二次确认，LLM 不可单独触发撤回）；
- 记忆提取 prompt 明确「仅提取明确表述的偏好/事实/决策，不臆测推断」，降低噪音与隐私风险；
- 全部写操作沿用现有 MCP 安全层：路径越界检测、`.md` 白名单。

## 9. 明确不做（排除项）

- **跨 Harness 插件封装**（Claude Code/Codex/Cursor 官方插件）：协议层已兼容（标准 MCP），封装留待有需求时再做；
- **多租户 Peer 隔离**：个人知识库无此需求，多工作区用资源路径隔离即可；
- **云端/多端同步**：保持零云依赖；若未来需要，走共享中心 git 同步方案（1.1 已回归）扩展；
- **技能全自动入库**：必须经人工审批，保持 PLW 可信度底线；
- **本地 LLM 推理服务**（omlx 类）：PLW 不托管推理（走远程 API 或 Ollama），本地向量化已由 fastembed 覆盖，不引入独立推理服务；
- **多 CLI Agent 终端多路复用**（herdr 类）：单用户本地无多 CLI 并发场景；待架构收敛 P4 多 DSH headless 并发落地时再评估。

## 11. 已实现与已知取舍

> 1.2 记忆模块落地后的已知取舍记录，供后续迭代权衡是否收敛。

1. **T8 采集语义：全局频率限流 vs 每轮触发** —— 过程级采集 hook 采用「每轮对话都记录 trace」的每轮触发语义，提炼侧再异步节流，而非在采集层做全局频率限流（如 N 轮 / 时间窗口限频）。好处是不漏采关键上下文，代价是原始 trace 体积随对话量线性增长（`memories/_raw/`）。
2. **T8 `_is_llm_error` 私有 import** —— 提炼 pipeline 为判断 LLM 提炼失败，直接跨模块引用了 `common` 的私有函数 `_is_llm_error`。属私有 API 依赖，若该函数后续改名 / 移除会破坏记忆提炼，届时应收敛为公开判定接口。
3. **T9 `search_memory` 每次重扫** —— 记忆检索未做「全量索引常驻缓存」，每次 `search_memory` 都重新扫描 `memories/*.md` 并加载 / 计算 embedding。实现简单、始终与落盘一致，代价是记忆库较大时检索延迟上升（当前个人量级可接受）。
4. **T10 seed 同时命中 wiki 优先** —— 知识星链 seed 构建时，若同一实体同时命中 wiki 概念与 `mem:` 记忆节点，优先归并到 wiki 概念节点，避免同一实体出现重复节点；记忆仅在 wiki 无对应概念时独立成 `mem:` 节点。
5. **T10 记忆节点 size 统计悬空实体** —— 记忆节点在知识星链中的 `size` 统计口径包含悬空实体（尚未被其他节点引用的记忆实体），与 wiki 节点按引用计数的口径不完全一致，图谱侧面积显示存在轻微偏差。
6. **T12 approve 错误码统一 400** —— 技能候选审批接口对参数 / 状态错误统一返回 400，未细分 404（候选不存在）/ 409（状态冲突）等语义码，前端统一按失败提示处理。
7. **T13 技能候选 UI 位置** —— 需求描述为「自动化控制台 Skill 页签」，实际 Skill 及其候选已实现在 Settings「能力供给」面板，故候选区块也置于该处，未新建自动化 Skill 页签，避免重复入口。
8. **T13 `mmJsAttr` 未转义双引号** —— 记忆页 `onclick="mmPromote('…')"` 是双引号包裹的 HTML 属性，`mmJsAttr` 只转义 `\` 与 `'`，若 slug 含 `"` 会破坏属性（当前 `_safe_slug` 只替换 `/ \ 空格`，LLM 生成的 slug 几乎不含引号，风险极低）。后续可补 `"` 转义收敛。
9. **T13 列表逐条补正文** —— `GET /api/memory/list` 对每条记忆再 `read_memory` 补 body，一次列表 N 次文件读；个人量级可接受，量大可改批量读 / 缓存。
10. **T13 promote 无服务端幂等** —— 同一记忆连续两次 `promote` 会覆盖 `_promoted/<slug>.md`；UI 已用 `status='promoted'` 禁用按钮兜底，服务端可再加一道「已 promoted 则拒绝」的幂等防护。
