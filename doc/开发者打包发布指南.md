# PersonLLMWiki 开发者打包发布指南

> 本文档面向**开发者**，介绍如何为 PersonLLMWiki 构建、测试与发布 Windows 分发包。
> 项目采用 **Python Embedded 免安装分发**方案，最终用户解压即用、双击启动、一键升级。

---

## 1. 概述

PersonLLMWiki 的发布包分为两种类型：

| 包类型 | 包含内容 | 大小（约） | 适用场景 |
|--------|---------|-----------|---------|
| **全量包** | Python 运行时 + 应用代码 + bat 脚本 | 250MB | 首次安装 |
| **增量包** | 仅应用代码（app/） | 15MB | 版本升级 |

> **桌面安装包（规划中）**：除上述 zip 分发外，还有基于 PyWebView + PyInstaller + Inno Setup 的桌面安装包方案（`.exe` 安装程序 + 原生窗口），面向最终非技术用户。详见 [PyWebView桌面窗口壳设计方案.md](PyWebView桌面窗口壳设计方案.md)。本文档目前仅覆盖 zip 打包流程。

分发包的核心设计是**三层目录分离**：

```
PersonLLMWiki-v1.0.0/
├── runtime/      ← Python 运行时（~30MB，仅全量包含）
├── app/          ← 应用代码（升级时覆盖）
├── resource/     ← 用户数据（升级时保留）
├── logs/         ← 日志目录
├── .env          ← 用户配置（首次安装时生成）
├── VERSION
├── 启动.bat
├── 停止.bat
├── 首次安装.bat
├── 升级.bat
└── README-用户指南.txt
```

- **runtime/** 与 **app/** 分离：升级时仅覆盖 `app/`，无需重新下载 Python 运行时。
- **resource/** 用户数据独立：升级不影响用户数据。

## 2. 环境准备

### 2.1 开发环境要求

| 项目 | 要求 |
|------|------|
| Python | 3.10+（开发环境，打包脚本运行用） |
| Git | 已安装并配置 |
| 网络连接 | 首次打包需下载 Python Embedded（约 20MB）及依赖 |

> **说明**：开发机的 Python 仅用于运行打包脚本，分发包内嵌的是 Python 3.12.8 Embedded（Windows x64）。打包脚本会自动下载并引导，无需手动准备。

### 2.2 目录结构

打包相关代码位于 `packaging/` 目录：

```
packaging/
├── fetch_runtime.py        # Python 运行时下载与引导（下载→解压→启用site→引导pip→装依赖）
├── build_release.py        # 主打包脚本（全量包/增量包）
├── scripts/                # 用户侧 bat 脚本（随包分发）
│   ├── 启动.bat
│   ├── 停止.bat
│   ├── 首次安装.bat
│   └── 升级.bat
└── versions.json.template  # 版本清单模板（升级服务器用）
```

| 文件 | 职责 |
|------|------|
| `fetch_runtime.py` | 下载官方 Python embeddable zip，启用 site-packages，用 `get-pip.py` 引导 pip，安装 `requirements.txt` 依赖 |
| `build_release.py` | 编排全流程：调用 `fetch_runtime` 构建 runtime → 复制代码 → 复制 bat → 打 zip |
| `scripts/*.bat` | 用户侧脚本，随分发包一起释放到包根目录 |
| `versions.json.template` | 在线升级服务器的版本清单样板，发布时填写实际 URL |

## 3. 打包流程

### 3.1 全量包（首次发布）

**全量包**包含完整的 Python 运行时和所有依赖，是用户首次安装所需的包。

**操作步骤：**

1. **更新版本号**：编辑项目根目录的 `VERSION` 文件，写入新版本号（如 `1.0.0`）。

2. **执行打包命令**：
   ```bash
   python packaging/build_release.py 1.0.0
   ```

3. **脚本自动完成以下流程**：
   - 下载 Python Embedded（已缓存则跳过）
   - 启用 site-packages（取消 `._pth` 中 `import site` 的注释）
   - 用 `get-pip.py` 引导 pip
   - 安装 `requirements.txt` 中的全部依赖到 runtime 的 site-packages
   - 复制应用代码到 `app/`
   - 复制 bat 脚本、`.env.example`、`VERSION`、用户指南
   - 创建 `resource/`、`logs/` 等空目录占位
   - 打包为 zip

4. **产出**：
   ```
   packaging/dist/PersonLLMWiki-1.0.0.zip
   ```

   脚本结尾会打印产物路径和体积。

### 3.2 增量包（版本升级）

**增量包**仅包含应用代码（`app/`），用于已安装用户的版本升级，体积小、下载快。

**操作步骤：**

1. **更新版本号**：编辑 `VERSION` 文件（如 `1.1.0`）。

2. **执行打包命令**（注意 `--update` 参数）：
   ```bash
   python packaging/build_release.py 1.1.0 --update
   ```

3. **脚本自动完成**：
   - 复制应用代码（排除 `resource/`、`.env`、`__pycache__` 等）
   - 写入新的 `VERSION`
   - 打包为 zip

4. **产出**：
   ```
   packaging/dist/PersonLLMWiki-1.1.0-update.zip
   ```

> **何时用增量包**：runtime 未发生大版本变化、依赖无重大变更时，一律用增量包。仅当升级了 Python 大版本或引入了不兼容的 native 依赖时，才需要重新发布全量包。

### 3.3 打包参数说明

`build_release.py` 的命令行参数：

| 参数 | 是否必填 | 说明 |
|------|---------|------|
| `version` | 是 | 版本号，格式如 `1.0.0` |
| `--update` | 否 | 生成增量包；省略时默认生成全量包 |

调用示例：

```bash
# 全量包
python packaging/build_release.py 1.0.0

# 增量包
python packaging/build_release.py 1.1.0 --update
```

## 4. 发布流程

### 4.1 准备版本清单

发布前，更新升级服务器上的 `versions.json`（参考 `packaging/versions.json.template`）。

每次发布新版本时，在 `versions` 对象中新增一条记录，并将 `latest` 指向最新版本：

```json
{
    "latest": "1.1.0",
    "versions": {
        "1.1.0": {
            "url": "https://your-server.com/PersonLLMWiki-1.1.0-update.zip",
            "date": "2026-08-06",
            "notes": "更新说明",
            "min_runtime": "1.0.0",
            "size_mb": 15
        },
        "1.0.0": {
            "url": "https://your-server.com/PersonLLMWiki-1.0.0.zip",
            "date": "2026-07-01",
            "notes": "首个正式发布版本",
            "min_runtime": "1.0.0",
            "size_mb": 250
        }
    }
}
```

字段说明：

| 字段 | 说明 |
|------|------|
| `latest` | 当前最新版本号，`升级.bat` 据此判断是否需要升级 |
| `url` | 该版本 zip 包的下载地址 |
| `date` | 发布日期 |
| `notes` | 更新说明，会展示给用户 |
| `min_runtime` | 所需最低 runtime 版本（用于判断是否需重新发全量包） |
| `size_mb` | 包体积（MB），展示给用户 |

### 4.2 上传文件

发布时需要上传三类文件到服务器：

| 文件 | 上传位置 | 说明 |
|------|---------|------|
| 全量包 zip | 下载服务器 | 首次分发给新用户 |
| 增量包 zip | 升级服务器 | 供 `升级.bat` 下载 |
| `versions.json` | **固定 URL** | 必须有稳定可访问的地址，配置在 `升级.bat` 的 `VERSIONS_URL` |

> **关键**：`versions.json` 的 URL 必须固定不变，因为 `升级.bat` 中硬编码了 `VERSIONS_URL`。zip 包的下载地址则写在 `versions.json` 里，可灵活调整。

### 4.3 分发方式

根据团队规模和场景选择合适的分发方式：

| 方式 | 适用场景 | 说明 |
|------|---------|------|
| 直接传 zip | 内部团队、U盘 | 最简单，手动拷贝分发 |
| 网盘下载 | 小规模分发 | 上传到网盘，分享下载链接 |
| 内部 HTTP 服务器 | 企业内部自动升级 | 配合 `versions.json` 实现 `升级.bat` 自动检测 |
| GitHub Releases | 开源项目 | 利用 GitHub 托管，可配合 Actions 自动化 |

## 5. 版本管理规范

### 5.1 版本号规则

采用**语义化版本（Semantic Versioning）**：`MAJOR.MINOR.PATCH`

| 位 | 含义 | 何时递增 |
|----|------|---------|
| MAJOR | 主版本号 | 不兼容的修改（如数据库结构重构、API 大改） |
| MINOR | 次版本号 | 新增功能，向下兼容 |
| PATCH | 修订号 | Bug 修复 |

示例：
- `1.0.0` → `1.0.1`：修复了一个 Bug（发增量包）
- `1.0.1` → `1.1.0`：新增功能（发增量包）
- `1.x` → `2.0.0`：不兼容升级，可能需重新发全量包

### 5.2 升级兼容性

升级机制基于以下原则，开发时务必遵守：

| 组件 | 升级时行为 | 说明 |
|------|-----------|------|
| `app/` 代码 | 增量包覆盖 | 这是增量包唯一更新的内容 |
| 数据库 | `app.py` 自动迁移 | 通过 `ALTER TABLE` 等自动执行，无需手动操作 |
| `resource/` 数据 | 完整保留 | 用户数据不被升级影响 |
| `seed/` | 升级时覆盖 | 升级后重启自动同步到运行时目录，新增→追加、变更→覆盖、用户独有→保留 |
| `runtime/` | 仅大版本升级时更新 | 需重新发布全量包 |

> **重要**：增量包**只**更新 `app/` 代码。如需更新依赖（`requirements.txt` 变化），`升级.bat` 会尝试用 runtime 内的 pip 重新安装依赖；但若涉及 native 依赖的重大变更（如 onnxruntime 大版本升级），应发布全量包。

## 6. 测试验证

### 6.1 打包后测试清单

每次发布前，按以下清单逐项验证：

- [ ] 解压全量包到**干净目录**（不含历史残留）
- [ ] 运行 `首次安装.bat`，确认无报错
- [ ] 双击 `启动.bat`（或桌面快捷方式），浏览器正常打开 `http://127.0.0.1:5000`
- [ ] 各功能模块可用（文档导入、对话、搜索等）
- [ ] 生成增量包，模拟升级流程
- [ ] 升级后数据完整（数据库、资源文件未丢失）
- [ ] 升级后版本号（`VERSION` 文件）已更新

> **建议**：在虚拟机或全新 Windows 环境中执行上述测试，避免开发机环境污染结果。

### 6.2 常见打包问题

| 问题 | 原因 | 解决 |
|------|------|------|
| pip 引导失败 | 网络问题，无法下载 `get-pip.py` | 检查网络；或手动下载 `get-pip.py` 放入 runtime 目录后重新执行 |
| 依赖安装失败 | 某些包无 Windows wheel | 检查 `requirements.txt`，确认所有依赖均提供 `win_amd64` wheel |
| 体积过大 | `fastembed` / `onnxruntime` 等体积较大 | 可考虑后期拆分为可选依赖，按需安装 |
| `.env` 被打包 | 未在排除列表 | 确认 `.env` 在 `build_release.py` 的 `EXCLUDE_PATTERNS` 中（默认已排除） |
| 升级后启动失败 | 增量包代码与旧 runtime 依赖不兼容 | 回滚（`app_backup`），改发全量包 |

## 7. CI/CD 集成（可选）

### 7.1 GitHub Actions 自动打包

利用 GitHub Actions 在打 tag 时自动构建全量包和增量包：

```yaml
name: Build Release
on:
  push:
    tags: ['v*']
jobs:
  build:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build full package
        run: python packaging/build_release.py ${{ github.ref_name }}
      - name: Build update package
        run: python packaging/build_release.py ${{ github.ref_name }} --update
      - name: Upload artifacts
        uses: actions/upload-artifact@v4
        with:
          name: PersonLLMWiki-${{ github.ref_name }}
          path: packaging/dist/
```

> **提示**：tag 命名建议为 `v1.0.0` 形式。`${{ github.ref_name }}` 会解析为 `v1.0.0`，如需去掉 `v` 前缀可在脚本前做字符串处理，或在 `build_release.py` 内部兼容。

如需自动发布到 GitHub Releases，可在 workflow 末尾追加 `softprops/action-gh-release` 步骤，将 `packaging/dist/*.zip` 作为资产上传。

## 8. 升级服务器搭建

### 8.1 最简方案：静态文件服务

升级机制只需要一个能托管静态文件的 HTTP 服务器，无需后端逻辑。

**步骤：**

1. 使用 Nginx 或 Apache 托管 `versions.json` 和所有 zip 包：

   ```nginx
   server {
       listen 80;
       server_name updates.your-domain.com;
       root /var/www/personllmwiki;

       location / {
           autoindex on;
           types { application/json json; }
       }
   }
   ```

   目录结构：
   ```
   /var/www/personllmwiki/
   ├── versions.json
   ├── PersonLLMWiki-1.0.0.zip
   └── PersonLLMWiki-1.1.0-update.zip
   ```

2. 将 `versions.json` 的访问 URL 配置到 `升级.bat` 中的 `VERSIONS_URL`：
   ```bat
   set VERSIONS_URL=https://updates.your-domain.com/versions.json
   ```

3. 用户双击 `升级.bat`，脚本会自动：拉取 `versions.json` → 比较版本 → 下载增量包 → 备份 → 解压覆盖 `app/` → 更新 `VERSION`。

> **替代方案**：若无独立服务器，可将 `versions.json` 和 zip 包放在 GitHub 仓库中，使用 `raw.githubusercontent.com` 的 URL（即 `packaging/scripts/升级.bat` 中的默认值）。

### 8.2 版本回滚策略

当某个发布版本存在严重问题需要撤回时：

1. **修改 `versions.json`**：将 `latest` 指回上一个稳定版本：
   ```json
   {
       "latest": "1.0.0",
       "versions": { ... }
   }
   ```

2. **用户侧自动生效**：已升级到问题版本的用户，再次运行 `升级.bat` 时：
   - `upgrade_check.py` 比较版本时发现 `latest < current`（如 `1.0.0 < 1.1.0`）
   - 版本比较逻辑会判定为"需要更新"（目标版本可低于当前版本）
   - 自动下载 `1.0.0` 的包并应用，实现"降级"

> **注意**：回滚依赖上一个版本的 zip 包仍可下载。务必不要删除旧版本的 zip 文件，保留至少一个大版本周期内的历史包。
