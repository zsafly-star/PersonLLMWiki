> 版本：v1.0 ｜ 状态：设计论证稿（待审） ｜ 作者：AI 助手 + 用户共创
> 前置知识：本平台设计依托项目知识库已有概念——`主管-工作者模式`、`人在回路`、`react模式`、`agent_loop`、`router + skills 模式`、`规划模式`、`反思模式`、`四层分离架构`、`zssnote mcp 手写 handler`、`主流agent框架生态`。

## 1. 背景与目标

### 1.1 背景
用户希望通过"对话驱动 + 多智能体分工 + 人工审批闸门"的方式，在 PersonLLMWiki 项目中按需生产各类交付物（给项目增加 TODO 功能、写 PPT、年度总结等），并把每个任务做成可追踪、可中断、可断点续跑的独立工作单元。

当前项目已具备 MCP 工具链（zssnote handler / SAP 物料查询 / 规格书提取 / 文档创建 / PDF 处理），可作为能力执行层的基础。

### 1.2 目标
- 用"流水线 + 人工闸门"的方式，把一句自然语言需求落成可执行的交付流水线。
- 长时任务（跨多天、多次确认）可独立承载、断点续跑、多任务并行切换。
- 新增场景（写 PPT / 年度总结）= 注册一份流程定义，不改主程序，实现平台化扩展。
- 全程权限受限、数据防外带、全量审计，满足单人自用下的安全诉求。

### 1.3 非目标（本期不做）
- 多租户 / 多用户隔离（单人自用边界）。
- 隐私/合同等 L4 级高敏数据的完整加密合规体系（分段预留，暂不实现）。
- 生产级水平扩展与高可用。

## 2. 问题定义（三条核心判断 + 威胁模型）

### 2.1 三条核心判断（设计成立的前提）
| # | 判断 | 依据 |
|---|---|---|
| ① | 必须"流水线 + 阶段产物"，而非"一个 agent 一把梭" | `主管-工作者模式`：复杂任务拆解、主管集中调度、子任务可并行 |
| ② | 每个阶段产物必须过"人工闸门"审批 | `人在回路`：风险分级、关键节点强制人工审批 |
| ③ | 长时任务必须脱离会话、独立承载 | 工程推理 + 业界产品（ChatGPT Projects/Tasks、AI 编程 Agent）对标 |

### 2.2 威胁模型
核心资产：①项目源码 ②SAP 物料数据（库存/批次/规格书，涉商业秘密）③知识库文档 ④AI 关键决策。

风险源：A. 恶意/带毒输入（如 PDF 内的注入内容） B. 子智能体被 prompt 注入/越权欺骗 C. 本地恶意软件 D. 事故性越权（权限过宽） E. 供应链（第三方库/MCP 后门）。

核心安全命题（单人自用特殊性）：**最小权限 + 数据不外带 + 全量审计**，而非"挡住远程入侵"。

## 3. 架构总览（五层）

在 `四层分离架构`（入口壳 / 业务核心 / 通信 / 外部服务）基础上，显式增加"任务状态持久化层（L4）"以承载长时任务的独立生命周期。二者互补：四层解耦通信，L4 解耦生命周期。

```
L1 接口壳 / Router          意图→路由到场景 + 登记新任务 + 核准 scope
L2 任务编排 / 流程引擎       场景=节点序列+子智能体+闸门位置（LangGraph 候选层）
L3 能力执行 / agent loop     思考→调 MCP 工具→产出片段（共享能力池）
L4 状态持久化 / 任务仓库     每任务：节点/产物/待确认/历史/追踪矩阵  ← 命脉
L5 产物与知识               文件 / 知识库 / 导出文档落盘
```

分层依据：状态/上下文管理难（`主管-工作者`痛点）→ L4 独立承担；单点瓶颈（单人可接受，不追求扩展）；跨层复用（L3 共享能力池，新场景只加 L2）。

## 4. 任务模型 与 L4 状态记录 Schema

### 4.1 任务 = 场景流程定义（类）+ 实例状态（对象）
新增场景无需造系统，只需注册一份流程定义；每条实际任务是该定义的一个带自身状态的实例。"怎么做（流程定义）"与"做到哪（实例状态）"解耦。

### 4.2 L4 状态记录 Schema（定稿）
```json
{
  "task_id": "TODO-001",
  "scene": "software_delivery",
  "state": "running | awaiting_user | done | failed | failed_pending_recovery | paused",
  "current_node": "node_key",
  "plan": [
    {"node": "requirement", "unit": "requirement_unit", "agent": "doc_writer", "gate": true},
    {"node": "prototype",   "unit": "prototype_unit",   "agent": "proto_agent", "gate": true},
    {"node": "develop",     "unit": "development_unit", "agent": "code_agent",  "gate": true}
  ],
  "artifacts": {"requirement": "path/draft.md", "prototype": "path/mockup", "code": "path/src"},
  "pending_approval": {
    "node": "prototype",
    "question": "请确认原型",
    "buttons": ["confirm", "reject"],
    "ai_recommended_plan": {"next": ["进入开发单元"], "node_count": 3, "eta_minutes": 15}
  },
  "traceability": [
    {"req": "增加TODO入口", "covered_in": "prototype", "status": "ok"}
  ],
  "history": [
    {"time": "2026-xx-xxT09:00", "event": "创建任务", "by": "user"},
    {"time": "2026-xx-xxT09:05", "event": "需求单元完成", "by": "agent"}
  ],
  "timestamps": {"created": "...", "updated": "...", "due": null}
}
```

字段取舍说明：
- task_id / state / current_node / history：借鉴通用任务模型（Jira/Trello）+ `人在回路` 待确认字段。
- pending_approval.ai_recommended_plan：对应"确认时展示 AI 下一步推荐"需求。
- due / traceability 粒度：以务实够用为准。

## 5. 状态机（含失败恢复）

```
            ┌────────────┐
            │  running    │◄──────────────┐
            └─────┬──────┘               │ 用户干预/重试
                  │ 节点完成              │
                  ▼                       │
            ┌────────────┐   高风险      ┌──────────────┐
            │awaiting_user│───────────►│failed_pending │
            │  (待确认)   │              │  _recovery    │
            └─────┬──────┘              └──────┬───────┘
                  │ 通过 / 自动放行             │ 重试/接管/忽略
                  ▼                           ▼
            下一节点 ◄──────────────────── 回到 running
                  │
                  ▼
              (全部节点完成) ───► done
```

关键说明：
- `failed_pending_recovery`：子智能体出错/超时/产出不达标/数据外带告警时进入；与 `awaiting_user` 并列置顶高亮；提供 [重试当前节点] [跳过并人工接管] [忽略继续]。
- `paused`：用户主动暂停长时任务。

## 6. 场景分层（单元场景 + 级联）

节点数偏少主张，多于则通过场景拆分级联：

- 场景 = 单元场景（每单元 3~4 节点，自己闭环、可单独确认、可独立断点/恢复/复用）。
- 单元可级联成复合流程。例「软件交付」=`需求单元`(确认) → `原型单元`(确认) → `开发单元`。
- 每单元内部 e.g.：①原材料 ②初稿 ③自审 ④交付；超过即触发单元拆分。

依据：`主管-工作者`的任务拆解思想递归应用 + `规划模式`的层层规划。L2 流程定义必须支持"子场景/子单元"嵌套。

## 7. 确认交互（AI 下一步推荐）

每当节点完成、交给你确认时，确认卡不仅展示产物，还展示 AI 推荐的下一步计划：
```
📋 AI 下一步推荐
基于当前产物，下一步建议：
 · 进入原型单元，首先生成线框
 · 若你希望，可先补充验收标准
 预计节点数：3 | 预计时长：约X分钟
[就这么办] [我来调整]
```
把"确认"从"你点头"升级为"在知情、看到 AI 计划后的高质量判断"。依据：`规划模式`（计划即产物）与 `人在回路` 的确认动作绑定。

## 8. 任务中心 UI 设计

### 8.1 为什么独立于对话框
长时任务跨会话、跨天、需多次确认，必须有独立于会话的持久身份与展示容器。对话框负责"发起/即时对话"，任务中心负责"承接/追踪/管理"。

### 8.2 页面结构
- **任务列表页**（默认落地页）：状态筛选（全部/执行中/等待审批/已完成/失败/恢复中）+ 待确认与恢复任务置顶 + 每行显示"第n单元·第m步/总步 + 状态徽章 + 是否待确认红点 + 最近更新"。
- **任务详情页**（点行进）：任务概览卡 + 单元/节点时间线 + 各节点产物预览 + 待确认区（[通过][提出修改][按建议办][我来调整]）+ 需求-交付物追踪矩阵 + 审计日志。

### 8.3 数据流
UI 只读 L4 状态仓库 + 订阅变更（SSE/WebSocket/轮询均可，单人本地轮询足够），前端不保存副本状态。

## 9. 安全与数据分级（横切关注点）

安全不是独立层、而是贯穿 L2/L3/L4 的横切关注点，否则易沦为摆设。

### 9.1 敏感度界定：两轴判定
"敏感不敏感"= **数据敏感度（静态 L1-L4）× 动作风险类型（动态）**。

**轴一：数据静态分级**
| 级别 | 举例 | 策略 |
|---|---|---|
| L1 公开/低敏 | 项目目录结构、公开笔记、素材 | 白名单内自动放行+审计 |
| L2 内部 | SAP 库存数量、批次号、产品描述 | 可读、不可外带/批量导出 |
| L3 机密 | SAP 成本/单价、SMB 规格书全文、未公开源码 | 只读进目标节点，读出打码/审计/防落盘 |
| L4 极高（预留） | 客户/员工隐私、合同 | 每次访问强制二次确认+加密+严格白名单 |

**轴二：动作风险动态分级**
| 动作 | 风险 | 策略 |
|---|---|---|
| 只读且不外带/不落盘 | 低 | 自动放行+审计 |
| 读取+写入产物/导出 | 中高（尤其含 L3） | **二次确认** |
| 批量读取/批量导出/跨场景复制 | 高（外带） | **强制二次确认** |
| 写入/覆盖/删除/连外网发送 | 极高 | **硬性二次确认+可回滚** |
| 访问白名单外 | 极高（越权） | **直接拦截**（不是确认） |

**合并判定规则**：
```
需二次确认 ⟺ (敏感度 ≥ L3 且 动作高风险) 或 (动作极高风险)
自动放行   ⟺ L1/L2 白名单内低风险 + 审计
直接拦截   ⟺ 越权 / 白名单外 / 疑似外带
```

### 9.2 场景资源白名单（最小权限落地表）
每个场景在 L2 流程定义中声明 `allowed_resources`，示例：
```json
{
  "scene": "software_delivery",
  "granted_actions": [
    {"resource": "project:personllmwiki:src_generated/*", "level": "L2", "actions": ["read", "write_generated_files"]},
    {"resource": "project:personllmwiki:src/*",            "level": "L2", "actions": ["read"]},
    {"resource": "kb:notes",                                "level": "L1", "actions": ["read"]},
    {"resource": "sap:material",                            "level": "L3", "actions": ["read_params_only"]},
    {"resource": "smb:specs",                               "level": "L3", "actions": ["read_pdf", "extract_params_only"]}
  ],
  "denied": ["sap:create", "project:outside_root/*", "export:full_docs_unless_confirm"]
}
```
权限逐节点递送、用完即回收；越权 → 直接拦截 + 红色审计告警 → 进 `failed_pending_recovery`。

### 9.3 五层嵌入
```
L1 Router   → 任务发起核准 scope，异常意图拦截
L2 编排     → 节点级权限递送（只给本节点最小 scope）
L3 执行     → 三层防护：工具白名单 / 参数沙箱(路径越界校验) / 内容级外带拦截
L4 状态     → 敏感数据不落原文只留指针；日志打码；敏感字段加密
L5 产物     → 敏感产物分离存储；导出按两轴判定是否需"确认导出"提示
审计贯穿     → 每次敏感操作写 history + sensitive_audit，可过滤可追溯
```

### 9.4 边界与已定决策
- 未来可能更敏感（L4 隐私/合同）：分级机制从第一天引入，将来加 L4 数据无需改架构，只需标级即获强确认+加密。
- SAP/SMB **只读取**：安全重点在"防外带"（读→写产物/批量）而非"防写入"。规格书 PDF 内容一律按不可信数据（不当指令执行），只提取白名单字段入知识库，原文不落盘。
- 二次确认不拖累：按两轴判定，低风险自动放行，仅高风险（L3 高敏+写/导出/批量）与极高风险触发确认。

## 10. LangGraph 定位与边界

- 采用人群：多场景平台 + 多任务并行 → **倾向引入**。
- **角色严格限定为 L2 任务编排引擎**（场景流程实例的图调度 + 断点/唤醒/并行实例）。
- **L3 每个节点内部仍是原生 agent loop（思考→调 MCP 工具→产出）**，不把每个工具调用铺成子图节点（避免过度图形化）。
- 明确受益点：`interrupt/resume`（人工确认挂起/唤醒）、多实例并行（每任务独立 state）、返工级联（更新依赖子图）。
- 若不引入、纯 MCP+agent loop+状态文件也可起步，但多任务并行与断点续跑的优雅度下降。

## 11. 落地里程碑

### M1（1-2 周）：核心闭环
只做 `需求单元`（对话 → 需求文档 → 你确认），用 L4 状态记录承载，验证状态持久化 + 断点续跑 + 两轴判定安全。

### M2：多任务并行验证
同时启动 TODO + 年度总结两任务，验证"各自独立挂起/唤醒、互不阻塞"。这是"多任务并行"成立的门槛。

### M3：平台化
抽出 Router 自动路由 + 场景流程注册表 + 共享能力池；正式让"新增场景 = 新增流程定义（含 allowed_resources）"成立；引入 LangGraph 至 L2。

## 12. 待确认项 / 风险提示
- `due` 截止时间、traceability 粒度是否还需更细，视实际痛点。
- 二次确认的"两轴阈值"是否要在真实使用中调参（L2/L3 分界线）。
- 后续若引入 L4 数据（隐私/合同），需同步补全加密与合规章节。
