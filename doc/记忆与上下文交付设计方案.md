# 记忆与上下文交付设计方案（OpenViking 替代）

> 版本：v0.1（2026-08）｜ 状态：设计稿，待评审｜ 关联文档：[PersonLLMWiki 设计规范](PersonLLMWiki设计规范.md)、[架构边界与升级指南](README-架构边界与升级指南.md)、[待办：架构收敛](待办-架构收敛.md)

---

## 1. 背景与目标

### 1.1 背景

本机集成过 OpenViking（自进化上下文数据库，`@openviking/dsh-memory-plugin`），其定位是面向 AI Agent 的「记忆 + 资源(RAG) + 技能」统一上下文底座。评估后认为其本机形态偏重：

- 依赖 Docker 服务端常驻（`127.0.0.1:1933`），服务端离线则召回/沉淀能力全部不可用；
- 与 PLW 的「知识 RAG」能力高度重叠，且 PLW 在可信度侧更强（人工审批、来源溯源、知识图谱）；
- 跨 Harness 兼容（Claude Code/Codex/Cursor）对本机「单 DSH 生态」用户无实际收益。

**目标**：PLW 补齐 OpenViking 的差异化缺口——**会话记忆自动提取、分层上下文交付、技能沉淀**，以单 Python 进程实现 OpenViking 的核心价值，去掉 Docker 服务端依赖。

### 1.2 替代范围对照

| OpenViking 能力 | PLW 现状 | 本方案动作 |
|---|---|---|
| 知识 RAG（resources） | ✅ 已有且更强（编译/审批/溯源/图谱） | 不动 |
| MCP 工具面 | ✅ 已有（19+ 工具） | 新增记忆类工具 |
| 会话记忆自动提取 | ❌ 无（`src/` 零 memory 实现） | **新增记忆模块**（§3） |
| 分层上下文交付 | ❌ 直接 Top-K 注入 | **新增 context_assembler**（§4） |
| 技能自动沉淀 | ❌ SKILL.md 仅手写 | **新增沉淀管道**（§5） |
| 跨 Harness 插件 | ⚠️ 仅绑定 DSH | 暂不做（§9 排除项） |
| 云端/多租户 | ❌ | 暂不做（§9 排除项） |

## 2. 总体设计

### 2.1 核心决策：记忆/知识双轨制

OpenViking 的哲学是「自动沉淀、随用随长」，代价是记忆带噪音；PLW 的立身之本是「人工审批、可信溯源」。两者不可互相污染，采用**双轨制**：

| 轨 | 内容 | 入库方式 | 可信度 | 生命周期 |
|---|---|---|---|---|
| **记忆轨** | 会话提取的偏好/事实/决策（碎片化、演进中） | 自动写入，`status=auto` | 低（标注来源对话 id） | 可一键撤回（revoke） |
| **知识轨** | Wiki 概念页（编译产物） | LLM 编译 → 人工审批 | 高（来源溯源 `^[source]`） | 审批制，LLM 不可自审批 |

- 记忆轨**不进入** wiki 概念索引，独立 `memories/` 目录 + 独立检索；
- 对话注入时记忆轨按「偏好/事实」加权靠前（个性化），知识轨按「查询相关度」排序（事实权威）；
- 记忆可被用户「转正」为知识：一键发起编译任务，把记忆条目作为文章源进入审批流。

### 2.2 架构位置

```
modules/memory/                     ← 新增模块（记忆轨）
├── extractor.py                    复用 wiki/compiler/extractor.py 的 LLM 提取
├── pipeline.py                     对话结束钩子 → 异步提取 → 去重 → 写入 → 索引
├── storage.py                      memories/*.md 读写（复用 wiki 页存储模式）
├── retrieval.py                    记忆语义检索（复用 wiki/compiler/retrieval.py，按 kind 过滤）
├── injector.py                     对话开场自动召回注入上下文
└── routes.py                       REST API + MCP 工具注册

common/context_assembler.py         ← 新增（分层交付，§4）

bin/skills/candidates/              ← 新增目录（技能沉淀草稿，§5）
```

### 2.3 与 DSH 的边界更新

原边界（[架构边界与升级指南](README-架构边界与升级指南.md)）：DSH 管「执行编排 + 记忆」，PLW 管「内容与企业能力」。

本方案将**记忆归属划入 PLW 知识底座**：PLW 已具备 LLM 提取 + embedding 索引 + 增量哈希全套基建，且记忆以 MCP 工具面（`mcp__personllmwiki__*`）供给，天然跨会话、跨 DSH 升级。DSH 仍管执行编排；PLW 提供「可检索、可注入、可撤回」的记忆资产。边界规则更新为：**PLW 管「知识 + 记忆」供给，DSH 管「执行编排」消费**。

## 3. 记忆模块

### 3.1 数据模型

存储为 Markdown + JSON frontmatter（与 wiki/concepts 一致），位于 `{RESOURCE_BASE_PATH}/memories/`：

```markdown
---
slug: 用户偏好-工作模式
kind: preference            # preference | fact | decision | other
status: auto                # auto(自动) | promoted(转正为知识) | revoked(撤回)
source_chat_id: 42          # 来源对话会话 id
created_at: 2026-08-24T10:00:00
embedding: ...              # 由索引写入，不入 md
---
正文：用户习惯在工作区先看 TODO 再开始编码。
```

关联概念：`[[相关wiki概念]]` 链接（若有），便于记忆 → 知识跳转。

### 3.2 提取管道

```
对话结束（POST /api/chat/sessions/<id>/close 或 SSE done 事件）
  → 异步任务（后台线程/APScheduler，不阻塞响应）
    → extractor.extract(对话摘要 + 消息)      # 复用 wiki/compiler/extractor.py，prompt 换为记忆提取
    → merger 去重合并（同 slug 近似条目，复用 wiki/compiler/merger.py）
    → 写入 memories/*.md（status=auto，带 source_chat_id）
    → 增量索引（复用 hasher.py SHA-256 变更检测，避免全量重算 embedding）
```

**触发时机**：会话自然结束（> N 条消息且有实质内容）或用户主动「记住本对话」；频率限制防噪音（如每分钟最多提取 1 次）。

### 3.3 召回与注入

- **主动注入**：对话开场，`injector.py` 自动 `search_memory(首条用户消息)` Top-3 注入系统上下文（与 Wiki 上下文并列，`---` 分隔）；
- **按需检索**：LLM 可通过 MCP 工具主动调 `search_memory`；
- **排序**：`preference/fact` 权重 > `decision/other`，且 `status=revoked` 一律过滤。

### 3.4 MCP 工具扩展

| 工具 | 说明 | 权限 |
|---|---|---|
| `remember` | 手动写入一条记忆（LLM 或用户经 UI 触发） | 写 |
| `search_memory` | 语义检索记忆，`kind` 过滤 | 读 |
| `list_memories` | 列出记忆（按 kind/时间/状态） | 读 |
| `forget_memory` | 撤回一条记忆（`status=revoked`，物理保留可审计） | 写 |

安全约束沿用现有规则：路径越界检测、不提供物理删除（撤回制）、LLM 不可自审批转正。

## 4. 分层上下文交付

### 4.1 目标

OpenViking 的核心差异点是「摘要 → 命中片段 → 原文」按需分层展开、控制 token 预算；PLW 现状是把 Top-K 片段一次性注入。新增 `common/context_assembler.py` 按预算组装。

### 4.2 组装策略

```
输入：query, 命中列表（含 wiki 页 summary + 片段 + 源文章路径）, budget_tokens, 目标层级
输出：分层上下文块

层1 摘要层：每个命中 wiki 页的 summary（~10% 预算）——让模型先有全局轮廓
层2 片段层：Top-K 命中片段 + 来源溯源（~60% 预算）——支撑具体论证
层3 原文层：需要精读的完整文章/页面（~30% 预算）——LLM 认为不够时经 MCP 工具二次拉取
```

- 层2 若预算不足则按相似度截断；层3 永不主动全量注入，由 LLM 调 `read_note`/`read_wiki_page` 按需拉取；
- 每层之间用结构化分隔符标注层级，便于模型区分「概要」与「事实」可信度。

### 4.3 接口

- **REST/MCP 兼容**：`search_kb` 扩展参数 `delivery=layered&budget_tokens=N`（默认保持 flat 兼容现有调用方）；
- **对话注入**：`common/agent.py` 的 Wiki 上下文注入改走 assembler，`expert` 模式强制分层组装。

## 5. 技能沉淀

### 5.1 流程

```
会话中 LLM 识别「可复用操作流程」（用户重复性任务/新工作流）
  → 生成 SKILL.md 草案（name/description front matter + 步骤指令，可附 scripts/）
  → 写入 bin/skills/candidates/<name>/SKILL.md（candidate 状态，不生效）
  → 前端「技能」标签页展示候选，复用 wiki 候选审批交互
    → 审批通过：移入 bin/skills/<name>/（skill_loader.py 扫描即生效，零重启）
    → 拒绝：删除候选目录
```

### 5.2 与现有机制衔接

- `common/skill_loader.py` 只扫描 `bin/skills/*/SKILL.md`，候选目录 `bin/skills/candidates/` 天然不加载——无需改动加载器；
- 审批交互复用 wiki 的 pending/approve/reject 模式（`WikiPage.status` 同款语义，新增 `SkillCandidate` 模型或复用表加 kind）。

## 6. 存储与索引变更

| 项 | 现状 | 变更 |
|---|---|---|
| 记忆文件 | — | 新增 `{RESOURCE_BASE_PATH}/memories/*.md` |
| 向量索引 | `wiki/embeddings.json`（全量） | 索引项加 `scope: wiki|memory` 字段，检索按 scope 过滤；或独立 `memories_embeddings.json`（推荐，隔离互不影响） |

## 7. 安全与隐私

- 记忆为本地文件 + 本地 embedding（fastembed ONNX），**零云依赖**，不随任何上传外泄；
- 撤回制（revoke）而非物理删除，保留审计可恢复；`forget_memory` 需要用户确认（前端二次确认，LLM 不可单独触发撤回）；
- 记忆提取 prompt 明确「仅提取明确表述的偏好/事实/决策，不臆测推断」，降低噪音与隐私风险；
- 全部写操作沿用现有 MCP 安全层：路径越界检测、`.md` 白名单。

## 8. 里程碑

| 阶段 | 内容 | 验收标准 |
|---|---|---|
| **M1 记忆 POC** | memories 存储 + 提取管道 + search_memory/list_memories + 对话开场注入 | 对话后可检索到提取的记忆；开场自动注入 Top-3 |
| **M2 分层交付** | context_assembler + search_kb layered 参数 + agent 注入改造 | 同查询对比 flat/layered 的 token 消耗下降且回答质量不降 |
| **M3 技能沉淀** | 技能候选目录 + 审批流 + 生效 | 审批通过的 SKILL.md 无需重启即被 skill_loader 加载 |
| **M4 收尾** | remember/forget_memory UI、记忆管理页、文档更新、边界文档同步 | 全链路可用，README/设计规范/边界文档同步 |

## 9. 明确不做（排除项）

- **跨 Harness 插件封装**（Claude Code/Codex/Cursor 官方插件）：协议层已兼容（标准 MCP），封装留待有需求时再做；
- **多租户 Peer 隔离**：个人知识库无此需求，多工作区用资源路径隔离即可；
- **云端/多端同步**：保持零云依赖；若未来需要，走共享中心 git 同步方案（1.1 回归后）扩展；
- **技能全自动入库**：必须经人工审批，保持 PLW 可信度底线。

---

## 10. 评审要点

1. 记忆轨是否需要独立 embedding 索引，还是并入现有索引加 `scope` 字段（推荐前者，隔离互不影响）；
2. 提取触发时机：会话结束钩子 vs 定时任务 vs 仅手动，是否要「自动 + 手动」双通道；
3. 记忆转正为知识的入口放对话页还是记忆管理页；
4. `search_kb` 扩展 `delivery` 参数是否影响现有调用方（DSH skill `personllmwiki-knowledge-base` 走默认 flat 不受影响）。
